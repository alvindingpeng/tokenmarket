## 2. 真正可继续开发的方向

### 2.1 平台可扩展性：插件化订阅平台（最大的一块空白）

**证据**: `docs/design-magpie-plugin-system.md`(455 行) 与 `design-magpie-smart-routing.md`(588 行) 是完整方案稿，
但 `grep magpie` 在 `internal/` 与 `web/src/` **零命中** —— 一行都没实现。

**当前的痛点是真的**：订阅平台被硬编码成 6 个常量
（`AccountPlatformCodex/Kiro/Gemini/Grok/Claude/Antigravity`），
全库 **180 处引用、20+ 文件**依赖它们。新增一个订阅平台要改 model / op / relay / subplatform 四层。

设计稿的关键结论（值得采信）: "插件系统"其实分两套 ——
内置插件（编译进主程序的 Go 包，只提供运行期开关）与外部插件（Bun/JS 子进程，**能自己声明 provider**）。
**能实现"加订阅账号"的是后者**。移植前者对加账号毫无帮助，这是个容易走错的方向。

**建议**: 若要动，先只做「provider 注册表」这一层（把 6 个常量变成可注册的 spec，
行为不变），验证扩展点是否够用，再决定要不要上 JS 子进程宿主。直接搬全套插件系统风险过高。

**收益**: 高（决定能不能持续接新上游）。**风险**: 高（碰 relay 热路径）。**前置**: 需真实新平台需求驱动。

### 2.2 多实例/多活：三个障碍一条都没动

设计稿 `design-multi-region-ha.md`、`design-app-multi-active.md` 齐全，实现为零。

| 障碍 | 现状（代码位置） | 为什么不能"加个锁"绕过 |
|---|---|---|
| 统计内存累计+全量快照覆盖写 | `op/stats.go` 多个包级 map + `StatsSaveDBTask` 定期整份盖回库 | 覆盖写**没有增量语义**: 两实例各持半份，谁后落库就抹掉对方增量 —— 是**丢计数**，且丢多少无法从库还原 |
| 限流内存桶 | `internal/ratelimit` 计数桶在进程内 map | N 个实例 = 实际额度 × N；同一 Key 打两个实例双双放行 |
| 后台任务进程内 ticker | `internal/task/task.go` 无库级租约（`grep lease_owner` 零命中） | 每实例各跑一遍：幂等任务浪费，非幂等（自动备份/告警推送/结算重试）就是重复动作 |

**建议**: 先做**障碍三**（库级租约选主）。它最独立、风险最低，
且 `balance_reservations.lease_expires_at` 已是同类模式的现成先例，可照抄。
统计与限流留到真有第二台机器再说。

> **2026-11-21 决定: 暂缓。** 单实例部署下库级租约选主收益为零 —— 只是给每个任务加一次
> "抢锁-续租-释放"的额外写。真要上多活时障碍一/障碍二必须先解决, 否则数据仍会算错。
> 详见 `docs/dev-next-2026-11-20.md` §B1。

### 2.3 【已交付 v1.10.14】四张核心业务表无留存策略（有真实数据证据）

> **状态**: 已交付。180 天留存 + 归档 NDJSON 落盘(含 `file.Sync()`) + 固化日汇总后再删;
> 归档失败则本轮一条不删。见 `docs/billing-retention-180d.md`。以下为原始分析, 保留作设计依据。

**证据**: `balance_reservations` / `balance_ledgers` / `billing_records` / `billing_settlement_tasks`
四张表在全库 `grep delete|retention|prune` **零命中**；而 `internal/task/names.go` 里有 5 个留存任务，
覆盖的是限流用量、归档文件、Webhook、视频任务 —— **这四张都不在内**。

**为什么不能直接删（真正的难点）**:
`BillingReleaseStale` 用 `NOT EXISTS (SELECT 1 FROM billing_settlement_tasks WHERE reservation_id = ...)`
判断"这笔预扣有没有结算意图"。**删行会让等待结算的预扣被当成泄漏释放 —— 钱会退错**。
`billing_settlement_tasks` 当初只能清 `snapshot` 列、不能删行，就是这个原因。

**可做的最小安全版本**: 只删「已结算 + 超期 + 无对应结算任务 + 对应 ledger 已归档」的 reservation 行；
`balance_ledgers` 走"归档 NDJSON 后再删"（与审计归档同模式）。
需先定留存期（建议 180 天，与审计一致）。

**收益**: 中。**风险**: 高（碰钱）。

### 2.6 并发写入抖动（v1.10.16 已交付, 原清单外新发现）

压测与错误日志暴露了一个**不在任何设计稿里**的真缺陷: SQLite WAL 下"先读后写"的事务
在写的那一刻要把读快照升级成写事务, 升级窗口内只要有别的提交就被拒绝并返回
`SQLITE_BUSY_SNAPSHOT`(517) —— `busy_timeout` 不覆盖这条路径, 只能整事务回滚重来。

实测(6 路热写 + 4 路短读后写): 短事务失败 **21136 次**; 全局 `-txlock=immediate` 无效且
让只读事务挡写入者 1.032 秒; `busy_timeout` 调大同样无效。

修法: 只在**短的读后写事务**开头执行一次零命中的空更新(`db.AcquireWriteLock`), 17 处定点覆盖。
修复后短事务失败 **0**, 热路径 p99 34.4ms → **2.45ms**, 日结失败 24/26 → **0**。
取锁本身零成本: 2000 次取锁后 WAL 增量 **0 字节**、锚点表仍 **0 行**。

详细数据与判断标准见 `CHANGELOG.md` v1.10.16 与 `docs/dev-next-2026-11-20.md` §A3。

## 4. 一句话结论

v1.10.13 的**功能面已经相当完整**（计费、钱包、提现、汇率、渠道治理、Webhook、工单、2FA、告警静默全都有），
它不是"缺功能"，而是缺**三个结构性能力**：可扩展的订阅平台、可水平扩展的运行时、
以及让这些能力可信的**测试稳定性**。功能清单上还能加的项，多半是设计稿里明确不做的。
