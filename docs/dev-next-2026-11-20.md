## 判断依据

核对方式: 对每项能力在代码里 grep 求证——路由是否注册、模型是否建表、任务是否登记、

## A. 有明确证据的缺陷（建议优先）

### A1. 【已交付 v1.10.14】`balance_reservations` / `balance_ledgers` 无清理任务

> **状态**: 已随四张资金表留存策略一起交付(详见 `docs/billing-retention-180d.md`)。
> 180 天留存 + 归档 NDJSON 落盘 + 固化日汇总后再删, 归档失败则本轮一条不删。
> 下面保留原始分析作为设计依据, 不再作为待办。

**证据**: `internal/task/names.go` 里有 `rate_limit_usage_retention`、`archive_retention`、
`webhook_cleanup`、`video_job_cleanup`, **没有**针对这两张表的留存任务;
全库 grep `balance_reservations` + `delete/retention/prune` 无命中。

**影响**: 两表持续增长（文档记载曾达 15514 / 31031 行, 日均 +621 / +1242）。
SQLite 单表变大后索引与 VACUUM 成本上升, 备份文件随之变大。

**为什么不能"直接删"**（这是本项真正的难点, 不是写个 DELETE）:
- `BillingReleaseStale` 用 `NOT EXISTS (SELECT 1 FROM billing_settlement_tasks ...)` 判断
  "这笔预扣有没有结算意图" —— **删行会让等待结算的预扣被当成泄漏释放, 钱退错**。
  （这是 `billing_settlement_tasks` 当初只能清 `snapshot` 列、不能删行的同一个原因。）
- `balance_ledgers` 是**权威留痕**, 对账与提现审计依赖它。

**可做的最小安全版本**: 只删「已结算 + 超期 + 无对应结算任务 + 对应 ledger 已归档」的
`balance_reservations` 行; `balance_ledgers` 走"归档到 NDJSON 后再删"的路径（与审计归档同模式）。
需要先定留存期（建议 180 天, 与审计一致）。

**收益**: 中。**风险**: 高（碰钱）。**前置**: 必须先明确对账证据策略。

### A2. 【已澄清: 已在 v1.9.x 解决, 且本条归属记错了】部署脚本的 `pre-*` 整库副本无轮转

> **2026-11-21 复核结论**: 本条**已经处理过了**, 而且原描述**张冠李戴**。
> `deploy/swap_deploy.sh` 只操作 `bin/`, 从不产生 `pre-*` 目录; 真正的整库副本在
> `/opt/switchyard/data/releases/<时间戳>-{security-batch2, -deploy, financial}`, 由
> `security-batch2-backup.py` / `deploy-security-batch2.py` / `production-financial-release.py` 写入。
> 轮转已由 `scripts/releases-retention.py` 实现: 只轮转 `*-security-batch2-deploy` 的**完成态**(保留 5 份),
> `*-financial` 与 `*-security-batch2` **永不轮转**(前者是财务证据, 后者是回退到迁移前 schema 的唯一途径)。
> 详见 `docs/backlog-unimplemented.md` 的更正段。**不再作为待办。**
> 下面保留原始分析, 作为"照文档改代码会改错脚本"的反面教材。

**证据**: `deploy/swap_deploy.sh` 已给**二进制**加了轮转（保留 10 份 `switchyard.prev-*`）,
但文档 §B3 记的 `pre-*` **整库目录副本**在仓库内找不到对应清理逻辑。

**影响**: 磁盘增长与**部署次数**线性相关, 与业务量无关。文档记载曾占 996 MB / 1.2 GB 备份目录。

**做法**: 照抄二进制轮转的模式（`ls -1t | tail -n +N+1 | rm`），保留最近 N 份（建议 5）。
只匹配自己产生的 `pre-*` 前缀, 不碰运维手工放入的文件。

**收益**: 小-中。**风险**: 低。**工作量**: 半小时。

### A3. 【已交付 v1.10.16】SQLite 并发写入抖动: 短事务读后写必须先取写锁

**这一条不在最初清单里, 是本轮"重检功能流程"时从压测与错误日志里挖出来的真缺陷。**

压测下转发写入偶发 `database is locked`, 日结单生成在并发时大面积失败, 延迟出现秒级尖刺。
两条"直觉修法"都被实测否掉: 调大 `busy_timeout` **完全不覆盖**真正的那条错误路径;
全局开 `_txlock=immediate` 会让只读事务去抢写锁(一条 1 秒的只读事务把写入者挡 1.032 秒)。

**根因**: WAL 下"先读后写"的事务在写的那一刻要把读快照升级成写事务, 升级窗口内只要有别的提交,
就被拒绝并返回 `SQLITE_BUSY_SNAPSHOT`(517) —— 这条路径**不看** `busy_timeout`, 唯一出路是整事务回滚重来。

**修法**: 只在**短的读后写事务**开头执行一次零命中的空更新(`db.AcquireWriteLock`), 让事务
在第一条语句就变成写事务。覆盖 17 处; 判断标准是"第一条语句是写的不改、只读的不取锁、长事务不提前取锁"。

**实测收益**: 短事务失败 21136 → **0**; 热路径 p99 34.4ms → **2.45ms**; 日结失败 24/26 → **0**,
日结 p50 561ms → 62ms。取锁本身的代价是 2000 次取锁后 WAL 增量 **0 字节**、锚点表仍 **0 行**。

**附带结论**: 仅拉长重试窗口(750ms → 1.1~1.7s, 10ms 起指数退避截顶 500ms + 正向抖动)单靠自己也救不回来(实测 8 次里仍失败 6 次),
重试只能兜底; 真正起作用的是锁的获取顺序。详见 `CHANGELOG.md` v1.10.16。

**收益**: 高(直接影响线上错误率与延迟)。**风险**: 中(碰所有资金写入路径, 已由 17 处定点 + 并发测试钉住)。

## B. 有设计稿、仍整篇未落地

### B1. 多实例 / 多活 —— 三个核心障碍一条都没动

设计稿: `design-multi-region-ha.md`、`design-app-multi-active.md`

| 障碍 | 现状 | 为什么不能"加个锁"绕过 |
|---|---|---|
| 统计内存累计 + 全量快照覆盖写 | `stats.go` 七个进程内累加器, `StatsSaveDBTask` 定时整份盖回库 | 覆盖写**没有增量语义**: 两个实例各持半份, 谁后落库就抹掉对方的增量 —— 是**丢计数**, 且丢了无法从库里还原 |
| 限流内存桶 | `internal/ratelimit` 计数桶在进程内 map | N 个实例 = 实际额度 × N。同一 Key 打两个实例双双放行 |
| 后台任务进程内 ticker | `internal/task` 无库级租约 | 每个实例各跑一遍: 幂等任务只是浪费, 非幂等（自动备份、告警推送、结算重试）就是重复动作 |

**建议**: 若要动, 先做**障碍三**（库级租约选主）。它最独立、风险最低,
且 `balance_reservations.lease_expires_at` 已是同类模式的现成先例, 可照抄。
统计与限流留到真有第二台机器时再做。

> **决定（2026-11-21）: 暂缓，不在本轮做。** 原因不是风险，而是**收益为零**:
> 单实例部署下库级租约选主只会给每个任务加一次"抢锁-续租-释放"的额外写, 换来的是
> 一个当下不存在的并发场景的保护。真正要上多活时, 障碍一(统计全量覆盖写丢计数)、
> 障碍二(限流额度 ×N)都得先解决, 否则只做选主只是把任务的重复执行消掉, 数据仍会算错。
> 该项保留在 P3 观察位, 等真有第二台机器的需求再启动。

**收益**: 高（但只在真要多活时）。**风险**: 高。**前置**: PG + 主备集群。

## D. 验证缺口（不是功能, 但会限制发布信心）

- 登录态页面与**真实交易全流程**未验收（充值/提现未用真实资金测过）
- MySQL / PostgreSQL **真实服务集成**未做（`financial-hardening-phase2a.md:64`）
- `-shuffle` 顺序依赖: 基线版原先约 10 个, **已修到 0**(见 `internal/op/testcache_export.go`)。
  根因不是"某两个用例互相影响", 而是**进程级缓存的寿命跟着进程、不跟着库**: 每个用例各换
  一次 `db.InitDB`, 而 `settingCache`/`userCache`/`channel*`/`group*`/`llmModel`/`apiKey*`
  等包级变量仍存着上一个库的值。换库前调用 `resetProcessCaches()` 即可;
  实测 8 个随机种子全绿。
  **本轮又补一处**: `TestShouldStoreBody` / `TestLogRetentionDaysDefault` 断言的是**出厂默认**,
  但同一包里 `TestLogLifecycle*` 会把 `log_retention_days` 写成 1, 于是 shuffle 下"默认值"
  变成"上一个用例留下的值"(6 个种子里红 1 个)。已给两者加 `logSettingsDefaultEnv(t)`, 连同缓存
  一起重置; 修复后 10 次 shuffle 零失败。

## F. 如果目标是"更强的产品"而非"更稳的运行"

上面 A-D 都是**运维/可靠性**视角。如果更看重**对客能力**, 按缺口大小排序:

1. **团队/组织协作** — 当前权限模型是"角色 + 归属", 没有"同一个账号下多人协作"的概念。
   （这条在 SaaS 版已由多租户解决, 非 SaaS 版天然不需要 —— 除非要做私有化部署。）
2. **对客用量报表** — 【v1.10.18 已交付一半】**按 Key 的持久化用量报表**: 设置页每把 Key 的弹窗
   现在能看「最近 30 天 / 累计」用量与实付、退费单列提示、并可导出该 Key 的明细 CSV; 数据来自
   `billing_records ∪ billing_rollups`, 所以明细被 180 天留存清理后该 Key 的历史仍然可查(归档时
   给汇总表加了第五个维度 `apikey`)。**仍未做**: 按项目/分组的月度成本报表、报表订阅推送。
   口径上限见 `docs/feature-analysis-v1.10.13.md` 与 `CHANGELOG.md` v1.10.18: 本版本之前已归档的
   明细没有 apikey 维度汇总行, 更早的 Key 历史无法补回, `coverage_start` 如实给出最早可见的一天。
3. **模型广场的可下单闭环** — P1/P2/P3 已交付（挂牌/加入配置/质量对比）,
   但仍是"看 + 配置", 没有自助下单/试用。
4. **开放 API 的版本化与配额契约** — `openapi_admin*.go` 有管理端 OpenAPI,
   但没有面向第三方的版本化契约与 SDK。

> 注: 第 1 条与 SaaS 版重叠。若将来想把 SaaS 能力**回流**到基线版,
> 应只回流"租户维度账单聚合"与"平台/租户闸门"两块, 而不是整包 —— 详见
> `octopus/docs/saas-progress.md` §3 的三条约束, 那些坑在回流时会原样复现。
