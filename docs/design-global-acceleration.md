# 全球接入与上游加速方案

> 状态: 设计稿, 未实施。
> 本文接在《design-multi-region-ha.md》P1/P2/P3 之上, 补齐该文未覆盖的**「网关 → 上游」**一段, 并把"全球用户调 API 提速"从 P1 的静态资源范围扩展到接口范围。

## 0. 结论先行

| 目标 | 现状 | 结论 |
|---|---|---|
| 全球用户 → 网关 | 实测近 7 天只有 **1 个真实客户端 IP**, 尚无全球流量 | 多区域部署现在做是盲投; 先做**边缘接入**(零代码改动), 拿到确定收益 |
| 网关 → 上游 | 19 渠道 **0 个走代理**; TTFT p50 **3.4s** / p95 **19.1s**, 渠道间差 **4.5 倍** | 主要瓶颈是**上游服务商质量**, 不是我们的传输; 第一杠杆是"选对渠道/出口", 第二才是传输优化 |
| 可观测性 | 只有 TTFT/总时长两个数, 无法区分「上游慢」与「我们到上游慢」 | **必须先补归因埋点**, 否则任何加速都无法验收 |

一句话: **先修确定性缺陷 + 补归因(G0/G1, 纯软件 1.5 周) → 边缘接入让 API 也走就近 PoP(G2, 1 周) → 出口池按实测打分选路(G3, 2-3 周) → 真正的区域级消除回源 RTT 才需要多区域(G4, 复用 P2/P3)。**

## 1. 线上实测数据(2026-10-11 ~ 10-18, 只读查询)

| 指标 | 数值 |
|---|---|
| 请求量 | 2664 次 / 7 天(约 380 次/天) |
| 成功率 | 98.0% |
| 流式占比 | 2619 / 2664 = **98.3%**(TTFT 是核心体验指标) |
| 客户端 IP | 2 个(1 个真实客户端 + 127.0.0.1) |
| 渠道 / 走代理 | 19 个 / **0 个** |
| TTFT 分位 | p50 **3360ms**, p90 12428ms, p95 **19113ms**, p99 27420ms |

按渠道的 TTFT(p50 / p95):

| 渠道 | 请求数 | p50 | p95 |
|---|---|---|---|
| workbuddy | 493 | 2225ms | 3683ms |
| cun.ai | 974 | 2492ms | 4477ms |
| itkk.lol | 33 | 5252ms | 9051ms |
| monk | 144 | 6163ms | 18482ms |
| sharellm.net | 424 | **7180ms** | 19657ms |
| 河图 | 279 | 7747ms | 24794ms |
| newx5m5x | 214 | 9971ms | 26492ms |

三条结论:

1. **入口没有全球流量**。当前是单客户端单地区, "全球提速"是**为未来就位**, 不是修当下的痛。
2. **上游离散度远大于传输优化空间**。渠道 p50 从 2.2s 到 10s(4.5 倍, 差 7.7 秒), 而传输层能优化的是每次请求 0.1–0.6 秒。所以上游加速的第一优先级是**选路质量与出口质量**, 不是 TCP 参数。
3. **选路有可疑点**。`route_metrics` 里存在 `ema_success=0.00` 的成员仍累计了 176–286 个样本; 而 p50 7.2s 的 sharellm 仍承接了 424 次请求。需要用 G0 的数据复核选路权重与失效成员剔除是否生效。

## 2. 链路预算: 钱花在哪一段

```
用户(地区A) ──①──> 边缘PoP ──②──> 网关源站 ──③──> 上游 ──④──> 生成
              TLS终结     长连接回源      DNS+建连+TLS+首字节
```

| 段 | 现状可测? | 量级 | 优化手段 |
|---|---|---|---|
| ① 用户→网关 | **完全不可测**(无 region, 无握手耗时) | 跨洋 TLS 1-2 RTT × 150-250ms | G2 边缘终结 TLS |
| ② PoP→源站 | 同上 | 跨洋 RTT, 长连接可摊薄 | G2 keepalive; G4 才能消除 |
| ③ 网关→上游 | **只能测到 ③+④ 合计**(TTFT) | 100-600ms 建连 + 上游排队 | G1 连接复用 + G3 出口择优 |
| ④ 上游生成 | 不可控 | 占比最大 | 选更好的服务商/渠道 |

**关键缺口**: 现在唯一的数 TTFT 是 ③+④ 的合计。不拆开就永远无法回答"该换上游还是该加出口"——这是 G0 存在的理由。

## 3. 方案

### G0 归因埋点(3 天, 所有后续工作的验收前提) — **已实施 v0.35.0**

已交付:

- `relay_requests` 与 `relay_request_attempts` 增列: `client_country`、`egress_id`、`dns_ns`、`connect_ns`、`tls_ns`、`ttfb_ns`、`conn_reused`(由 AutoMigrate 补齐, 存量行默认 0/空, 无需手写迁移)
- 采集器 `internal/rhttp/timing.go`: `httptrace.ClientTrace` 打点, 挂在每轮 `roundCtx` 上, 同协议透传与跨协议转换两条路径都覆盖
- 地区 `internal/geo`: 只认可信反代头(需 `server.trusted_proxies` 非空), 过滤 `XX`/`T1` 等占位值
- 聚合接口 `GET /api/v1/ops/latency?days=N` + 运维中心「延迟归因」页签: 按渠道 × 地区的 p50/p95
- 新增 `upstream_wait` 口径 = 首字节 − DNS − 建连 − TLS, 即上游自身排队时间

与原计划的差异(有意为之):

- `client_asn` 与 mmdb 解析**未做**(G0b): mmdb 需额外数据文件与许可证, 且边缘接入后头部信息更准, 现在做等于先造一个很快要被替代的组件
- 线上实测发现: 存在渠道直连 `http://<IP>:<port>`(明文 HTTP + IP), 其 DNS/TLS 段**必然为 0**, 首字节 2.3s 全在上游排队。看板文案与字段注释已明确这三种为 0 的情况, 避免被读成"我们连得很快"

原始计划条目:
- 采集: `internal/rhttp` 用 `httptrace.ClientTrace` 打点(DNSStart/DNSDone、ConnectStart/Done、TLSHandshakeStart/Done、GotFirstResponseByte)
- 国家: 优先取边缘注入头(`CF-IPCountry` / `X-Geo-Country`), 无边缘时用本地 mmdb 查 `client_ip`(零外部依赖)
- 看板: 「国家 × 渠道 × 出口」的 TTFT / 建连 P50/P95
- 验收: 能回答"cun.ai 的 2.5s 里有多少是建连、多少是上游排队"

### G1 出口确定性加固(1 周, 纯软件, 无外部依赖) — **已实施 v0.36.0**

**G1.1 修连接池缺陷(最高优先级, 半天)** — 已完成
`resolveUpstreamClient` 对渠道专用代理调用 `rhttp.New()`, 而 `rhttp.New` 明确"不缓存连接池", 且返回的 `CloseIdleConnections` 被调用方在每次请求结束时执行。改为 `rhttp.Shared(proxyURL)`: 按代理地址缓存客户端, 同一代理下的所有请求共用一个连接池, 后台按"15 分钟未使用"回收(管理员改代理地址后旧连接池不会永久占着)。同时删掉了贯穿 `upstreamResponse`、`handler`、`videotask` 的 `closeIdle` 回调 —— 这套"用完就关"的管线本身就是缺陷的一部分。
> 当前 0 个渠道走代理, 所以这是**潜伏缺陷**: 一旦为加速给渠道配代理, 每个请求立刻多付 1-3 个 RTT。

**G1.2 传输层参数(半天)** — 已完成
`MaxIdleConnsPerHost` 原为 Go 默认 **2**(并发超过 2 就反复重拨), 现为 64; `MaxIdleConns=256`、`IdleConnTimeout=90s`、`ForceAttemptHTTP2=true`。参数集中在 `clonedDefaultTransport` 一处维护, 并有测试守着不被改回默认。
> **DNS 缓存未做(有意跳过)**: G0 实测新连接 DNS 段只有 6ms, 而首字节 2300ms 量级; 且连接复用修好后 DNS 只在新连接时发生。为此引入自定义解析器要承担 Happy Eyeballs 退化与 SOCKS/代理路径不解析的风险, 收益不成比例。真需要时再做。

**G1.3 失效成员治理(1-2 天)** — 已完成, 但与原计划判断不同
原计划写的是"补持续低成功率自动降级", 实际读代码发现**熔断已经存在**(auth/quota 立即硬熔断, 其余按计数阈值), 线上也确实在触发。真正的缺口是**熔断时长不递增**: 阈值 5 次 → 停 5 分钟 → 探一次 → 再失败, 永远同一档位。线上实证有两个成员累计失败 38/42 次、成功率 **0.00**, 熔断窗口一到期就又被选中。
改法是加 `breaker_trips`(自上次成功以来的熔断次数) + 时长按 2 的幂递增、封顶 `breaker_max_minutes`(默认 60), **成功一次即清零** —— 自愈的成员不会被历史次数长期压着。凭据级与渠道模型级都生效, 告警里带上"第几次"。

**G1.4 选路参数校准(1-2 天)** — 复核完成, 未改默认权重
用 G0 数据 + 代码复核了 `score` 模式: 它已有可靠性软惩罚(成功率低于下限时按 `rate/floor` 折减, 强度按样本置信度 `n/(n+5)` 缩放), 0% 成功率成员会被压到近 0 分垫底, 而不是靠硬门槛误伤"略低于下限"的成员。线上那些低成功率成员样本增长很慢(数天 38 条), 说明它们本就很少被选中, 不是"选路坏在挑它们"。
结论: **不动权重**。盲改默认权重会同时影响所有分组, 而在没有反事实证据的情况下, 改比不改更危险。等 G3 有出口维度的数据后再校准。

原始计划(保留供对照):

**G1.1 修连接池缺陷(最高优先级, 半天)**
`internal/relay/upstream.go:39` 的 `resolveUpstreamClient` 对渠道专用代理调用 `rhttp.New()`, 而 `rhttp.New` 明确"不缓存连接池", 且返回的 `CloseIdleConnections` 会在每次请求后关闭空闲连接 → **每个请求重新 TCP+TLS 到代理和上游**。改为按 proxy URL 缓存 client(引用计数 + 空闲回收), 复用现有 `rhttp.Proxy()` 的双检锁模式扩成 map。
> 当前 0 个渠道走代理, 所以这是**潜伏缺陷**: 一旦为加速给渠道配代理, 每个请求立刻多付 1-3 个 RTT。

**G1.2 传输层参数(半天)**
`MaxIdleConnsPerHost` 现为 Go 默认 **2**(项目未覆盖) → 并发超过 2 就反复重拨。建议 `MaxIdleConnsPerHost=64`、`IdleConnTimeout=90s`、`ForceAttemptHTTP2=true`, 并加 DNS 缓存(TTL 60s, Go 无内置解析缓存)。

**G1.3 失效成员治理(1-2 天)**
现有 breaker 有冷却, 但 `ema_success=0.00` 的成员仍持续被采样。补"持续低成功率自动降级"(低于阈值且样本数达标 → 暂停成员 + 告警), 验收标准是"0 次被选中"。

**G1.4 选路参数校准(1-2 天)**
用 G0 数据复核各分组的 mode 与权重(延迟/成功率/价格)。若分组是 `failover`/`manual`, 则"慢渠道承接大量请求"是设计使然而非缺陷 —— 需要和数据一起判断。

### G2 入口边缘接入(1 周, 零后端代码改动) — **已实施 v0.38.0(源站侧), 边缘待启用**

已交付(源站侧全部完成, 与边缘无关的部分):

- 拓扑: 客户端 --TLS--> Cloudflare 边缘(`prod.example.com`, 橙云) --HTTP--> 本机 nginx --HTTP--> switchyard(`127.0.0.1:8088`)
- 源站 vhost: `/etc/nginx/sites-available/switchyard-tt` —— 80 端口只做 ACME 校验与 301, 443 做反代
- 证书: Let's Encrypt, 续期改用 **webroot**(`/var/www/html`), `certbot renew --dry-run` 通过。原 `--nginx` 插件在自定义 vhost 上会挂起, 且每次续期都重写 vhost —— 会把手调的缓冲与 realip 配置冲掉, 故弃用
- 真实 IP: `set_real_ip_from` 取自 `cloudflare.com/ips-v4|v6`(当前 22 条) + `real_ip_header CF-Connecting-IP`, 不硬编码网段
- `CF-IPCountry` 只在来源属于 CF 网段时透传(`geo $realip_remote_addr` + `map`): 绕过 CF 直连源站拿不到可信国家码
- `server.trusted_proxies = ["127.0.0.1"]` —— 只信本机 nginx
- `X-Forwarded-For` 用 `$remote_addr` **覆盖**而非追加

必配项逐条落地: `proxy_buffering off`(全局, 不挑路径) / `proxy_request_buffering off` / `client_max_body_size 512m` / `proxy_read_timeout 600s` / `http2 on` / 到源站 HTTP/1.1 keepalive / HSTS

与原计划的差异:

- **"零后端代码改动"不成立**。四处必改(见 v0.38.0 CHANGELOG): 流式响应补 `X-Accel-Buffering: no`、调用方 IP 不再采信伪造的 XFF、登录 Cookie 的 `Secure` 跟随协议、支付回调基址与登录共用同一套协议判定。其中第一处不改会直接让流式失效 —— nginx 默认攒缓冲, 客户端表现为"卡很久然后一次性吐完"。
- **`trusted_proxies` 填 `127.0.0.1` 而不是边缘网段**。计划里写的是"填边缘出口网段", 但边缘网段会变且清单很长, 放进 Gin 意味着每次 CF 调整都要改应用配置并重启。改为本机 nginx 归一化后只信本机, 应用侧只有一个静态值。

源站侧实测结论:

- 真实 IP 落库正确, 伪造的 `X-Forwarded-For` 被忽略(记为真实来源而非伪造值)
- 非 CF 来源的 `CF-IPCountry` 被丢弃, 真实来源的国家码正常透传 —— 区域亲和(G3)可以真正上线
- 流式首字节 0.88s / 总时长 2.33s / 203 个事件块, 未被缓冲
- 自动续期演练通过, 且续期不再重写 vhost

边缘侧的三个硬限制(Cloudflare 免费版):

- 请求体上限 **100MB**, 超过在边缘就被拒; 源站的 512m 只对绕过边缘的直连生效
- 非流式请求 **100 秒**无字节即 524。当前 237 条请求里最大首字节 4.5s, 无风险; 但长生成与视频任务要盯着
- 边缘证书**按主机名逐个签发**, 新增子域要等签发完成才通 TLS(本次 `prod.example.com` 即卡在这一步)

待办(边缘启用):

- Cloudflare 后台把 `prod.example.com` 的边缘证书签出来(SSL/TLS → Edge Certificates → Universal SSL), SSL 模式设为 **Full (strict)** —— 源站已有有效 LE 证书; 设成 Flexible 会因源站 80→443 的 301 出现重定向循环
- 边缘证书就绪并验证后, 把 switchyard 监听从 `0.0.0.0:8088` 收到 `127.0.0.1:8088`, 关闭公网明文入口
- 可选加固: 443 只放行 CF 网段与内网(`allow ...; deny all;`), 彻底禁止绕过边缘直连源站。**不建议现在做** —— CF 调整网段时会导致整站不可达, 而当前收益有限

原始计划(保留供对照):


这是 P1 的**扩集**: P1 只把静态资源放边缘(明确说明"接口调用仍回源站"), G2 让 `/api` 与 `/v1` **也过边缘**——这才是"全球用户调 API 提速"。

- 拓扑: 边缘 PoP 终结 TLS → 静态资源本地命中 → `/api`、`/v1` 反代回源(长连接)
- 必配项:
  - `proxy_buffering off`(SSE 与流式生成, 否则首字被攒住)
  - 读超时 ≥ 600s(长生成), `client_max_body_size 512m`(生图/生视频)
  - 到源站开 HTTP/2 + keepalive
  - **`config.json` 的 `server.trusted_proxies` 填边缘出口网段** —— 现在默认 `SetTrustedProxies(nil)`(不信任任何代理), 上线边缘后所有 `client_ip` 会变成 PoP 的 IP, 直接破坏按 IP 限流、验证码防刷、审计留痕
- 收益与边界(诚实): 省掉跨洋 TLS 握手(1-2 RTT)与每请求建连, 但**源站 RTT 是地板**; 彻底消除它需要 G4
- 验收: 全球 5 个探针点 TLS 建连 p95 < 300ms; 首字节相对基线改善 ≥ 15%

### G3 出口池 + 按出口打分(2-3 周, 复用现有评分机制) — **已实施 v0.37.0**

已交付:

- 数据模型 `channel_egresses`: id / channel_id / name / kind(direct|http|socks5) / url / region / weight / enabled, 随 `model.Channel` 一起进进程内缓存, 编辑后下一轮选路立即生效
- 选路 `internal/relay/egress.go`: 复用成员指标的 EMA 结构与样本窗口(`memberMetric` + `applySample`), 额外一份失败冷却; 每轮独立选择, 因此某轮失败后下一轮可能换到另一条线路
- 冷出口按"已观测出口的平均值"参与, 不是 0 也不是无穷: 既不无条件抢占全部流量, 也不会永远轮不到
- 失败切路: 与成员冷却同源(`classCooldownSeconds`), 成功后解除; 全部冷却时探最早恢复的那条 —— 拒绝请求必然失败, 试一次仍有成功机会
- 区域亲和: `egress_region_bonus_ms` 设置项, 默认 **0 即关闭**(地区码来自反代头, 未配可信代理时恒为空, 开着也没效果)
- 归因: `egress_id` 落进 `upstream_timing`(G0 已预留该列), 运维中心「延迟归因」新增出口维度与出口列
- 前端: 渠道编辑页新增「出口」步骤(名称/类型/地址/地区/权重/启停), 按名称增量同步, 同名出口保留原主键
- 验收: 两个真实 HTTP 代理 + 一次真实转发, 摘掉最优出口后请求自动走另一条且不失败(`internal/relay/egress_proxy_test.go`)

与原计划的差异:

- **指标不落库**(只存进程内): 出口成绩几秒钟就能重新学到 —— 每条出口各被选中一次就有样本, 而一个不通的出口最多让一次请求失败。为它做持久化要动 `route_metrics` 的格式, 收益不成比例。
- **weight 不是流量配比**, 而是"同分优先 + 冷出口采样顺序"。按权重随机分流需要比当前系统更强的采样纪律(否则小权重出口永远拿不到足以判断的样本), 语义写清楚比假装支持更实在。
- **routeExplanation 未加出口字段**: 该决策在渠道加载之前就已算出, 那时还不知道本轮走哪条出口。改为登记一条路由事件 `egress:<名称>`, 在请求详情的路由事件里可见 —— 排查时同样能看到, 且不会让决策结构里出现"未知"字段。

原始计划(保留供对照):

- 数据模型 `channel_egresses`: `id, channel_id, name, kind(direct|http|socks5), url, region, weight, enabled`
- 指标维度: `memberMetricKey{groupID,itemID}` 增加 `egressID`(或独立 `egressMetrics`), **复用现有 EMA、样本窗口、可靠性下限**(`internal/relay/metric.go`)
- 选路: 渠道内先按出口的 wait EMA 选, 失败切下一个出口 + 冷却(复用 breaker); `routeExplanation` 增加出口字段便于排查
- 区域亲和(可选): 渠道/出口打 `region`, 用户国家匹配时加分, 权重默认 0(关闭)——即"欧洲用户优先欧洲出口"
- 前端: 渠道编辑页加「出口列表」, 交互与状态管理复用现有 `FormKeys`(凭据列表)的按名定位模式
- 验收: 单渠道配 2 个出口, 手动摘掉当前最优的那个 → 30 秒内自动切到另一个, 期间请求不失败

### G4 多区域数据面(按需, 不重复设计)

前置是既有文档的 P2(PG 主备 + Patroni)与 P3(统计增量/限流集中/任务选主), 本文只补一条:

- **按用户分区优于 active-active**: 同一 API Key 固定落到一个区域(GeoDNS + Key 亲和), 各区域只服务自己的用户 → 进程内指标/限流/熔断天然自洽, P3 的改造量可砍掉一半
- 触发条件: G2 上线后, 若仍有 >30% 用户的「握手 + 网络传播」占 TTFT 的 40% 以上, 才值得上 G4

## 4. 排期

| 阶段 | 内容 | 工作量 | 外部依赖 | 风险 |
|---|---|---|---|---|
| G0 | 归因埋点 + 看板 | 3 天 | 无 | 低(新增可空列) |
| G1 | 连接池/传输参数/失效成员 | 1 周 | 无 | 低(参数化可回退) |
| G2 | 边缘接入(API 过边缘) | 1 周 | 域名/证书/边缘服务选型 | 低(源站兜底) |
| G3 | 出口池 + 按出口打分 | 2-3 周 | 出口节点(代理/专线) | 中(触及选路核心) |
| G4 | 多区域数据面 | 按 P3 评估 | PG 集群 | 中高 |

**G0 + G1 可以立即开始**, 不需要任何采购或架构决策, 且是后面所有验收的基础。

## 5. 验收标准

| 维度 | 指标 | 目标 |
|---|---|---|
| 入口 | 全球探针 TLS 建连 p95 | < 300ms |
| 入口 | 首字节相对基线 | 改善 ≥ 15% |
| 出口 | 每请求建连开销(③ 中的 connect+tls) | p95 < 150ms |
| 出口 | 失效成员被选中次数 | 0 |
| 出口 | 出口故障切换 | < 30s, 请求不失败 |
| 全站 | 成功率 | 保持 ≥ 98% |
| 全站 | TTFT p95 | 相对基线改善 ≥ 20% |

## 6. 风险与回滚

- **边缘接入**: 源站始终可直接访问(内嵌前端是兜底), DNS TTL 设短可分钟级切回
- **连接池参数**: 全部走配置, 异常时改回默认值即可
- **出口池**: 默认"单出口 = 直连", 与现状行为等价; 新表可整体禁用
- **埋点**: 新列可空, 不影响现有读写与日志页

## 7. 明确不做

- 用 CDN 缓存任何 `/api`、`/v1` 响应(LLM 响应不可缓存且含用户数据)
- 资金链路(钱包/预扣/结算/兑换)参与双写或多活
- 未度量就上多区域部署
- 只加代理不修连接池(每请求多付 1-3 个 RTT, 越加越慢)
