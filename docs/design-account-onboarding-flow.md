# 应用流程设计: 账号接入 → 模型上架 → 账号运营

> 背景: 三个能力(导入账号 / 渠道模型上架 / 账号自动续期)后端都已实现,
> 但入口散落、账号导入后的生命周期没有管理面。本文先把**现状**说清, 再给**目标流程**,
> 最后列出需要改动的落点与取舍。

## 1. 现状: 三个入口的真实位置

| 能力 | 现在在哪 | 谁能看到 | 问题 |
|---|---|---|---|
| 导入账号 | 渠道**编辑**表单 → 凭据区右上角按钮 | admin / reseller | 必须先建渠道; 新建渠道时按钮不出现 |
| 模型上架 | `Share` 页 → 渠道卡片 → 改价工作台 | admin / reseller | 与"账号是否可用"完全脱节 |
| 账号续期 | 后台定时任务, 无界面 | 无人可见 | 导入成功后只剩一个 toast, 之后不可见 |

### 1.1 导入入口的实际约束

`FormKeys.tsx` 里这行是有意的:

```tsx
// 导入账号只在编辑已存在的渠道时出现: 新建渠道还没有可写的凭据表。
{channelId !== undefined && <AccountImport channelId={channelId} ... />}
```

也就是说,**要导入账号必须先把渠道建出来并保存**。第一次用的人会卡在这里:
他手上有一批账号, 但还不知道渠道该怎么配 —— 于是被迫先随便填一个 `base_url`
再回头导入, 而 `base_url` 对 OAuth 账号其实并不重要(令牌决定了去哪个上游)。

### 1.2 账号导入后的信息断层

库里有完整的账号元数据:

```go
AccountKind      // oauth / cookie
AccountPlatform  // codex / kiro / claude / gemini / grok
AccountEmail     // 展示用
TokenExpiresAt   // 到期时间, 定时任务据此提前刷新
TokenRefreshAt   // 最近一次刷新时间
```

但**前端一个都没显示**。凭据列表仍按老形状渲染 —— 名字 + 掩码串:

```
codex-real    sk-••••••••lder     <-- 用户看到的是这个
```

他看不到: 这是哪个平台、什么时候到期、上次刷新成功没有、这个账号还能不能用。
于是"定时验证有效性"这件事对使用者是**不可观测的** —— 账号静默失效时没有任何界面迹象。

## 2. 目标流程

把散落的三步串成一条主线, 并补上缺失的第四步(运营):

```
① 接入            ② 配置            ③ 上架            ④ 运营
导入账号  ──→  建渠道/编模型  ──→  审核 → 上架  ──→  看状态/续期/换号
   │                  │                │                  │
   │  账号独立于渠道    │  渠道是容器     │  闸门: 审核       │  缺口: 无界面
```

四项设计原则:

1. **账号先于渠道**: 账号不该是渠道的子表单。用户先有一批账号, 才决定怎么编排渠道。
2. **一处看全量**: 账号管理要有自己的页面, 而不是散在各渠道表单里。
3. **状态可见**: 到期/刷新/失效必须能在界面上看出来, 否则"自动续期"等于没做。
4. **失败要能出手**: 账号失效后必须有一键重导/换号的入口, 而不是删渠道重建。

## 3. 流程一: 接入(导入账号)

### 3.1 首选路径: 独立"账号"页导入

新增导航项 `accounts`(位于 `channel` 之后、`share` 之前), 页面提供:

```
┌─ 账号 ──────────────────────────────────────────────┐
│ [导入账号]  平台筛选: 全部/Codex/Kiro/Claude/...     │
│                                                    │
│ 名称        平台    状态      到期        操作      │
│ alice@x     codex   ● 正常    3天后       刷新 详情  │
│ bob@x       claude  ● 正常    28天后      刷新 详情  │
│ carol@x     kiro    ▲ 将到期  6小时       刷新 详情  │
│ dave@x      gemini  ■ 已失效  —           重导 删除  │
└────────────────────────────────────────────────────┘
```

**导入时可以选择"归到哪个渠道"**, 也可以先不归属(挂在暂存区)。
后者是当前流程最缺的一环: 账号先进来, 编排渠道是下一步的事。

这需要后端一个改动: `ChannelKey.ChannelID` 目前非空(凭据必须属于渠道)。
两种做法:

| 做法 | 代价 | 评价 |
|---|---|---|
| A. 加"暂存渠道"概念(虚拟渠道) | 低, 但会污染转发路径的候选集合 | ✗ 会让暂存账号被当作可用凭据 |
| B. 新增 `account` 表, 与 `channel_keys` 解耦 | 中: 新表 + 迁移 + 引用关系 | ✓ 语义干净 |
| C. 保持现状: 导入时必须选渠道 | **零** | 最小改动, 但没解决"账号先行" |

**建议先做 C 的改进版**: 导入对话框里加一个"目标渠道"下拉(默认选最近编辑的渠道),
并在渠道列表页也放一个导入按钮 —— 这样不必先钻进某个渠道的编辑表单。
真正的账号解耦(B)留到有明确需求时再做, 因为它的代价是数据模型变更,
而当前痛点(找不到入口)用 C 就能解决。

### 3.2 导入对话框要补的信息

现有对话框已经不错(平台 chips + JSON 输入 + 结果面板), 补三点:

1. **目标渠道选择**(见上)。
2. **导入前的字段预检**: 贴完 JSON 后本地先解析一遍, 当场提示"识别到平台 X / 缺少 refresh_token"。
   现在要等提交到服务端才知道错在哪, 一轮往返。
3. **批量导入**: 一次贴多个账号(JSON 数组或每行一个)。这是真实使用场景 ——
   手上有一批账号时逐个粘贴很痛苦。后端 `AccountImport` 已经是单条语义,
   批量只需在循环里调用并汇总每条结果。

## 4. 流程二: 配置(建渠道与模型)

这一步现状基本够用, 但有一个顺序陷阱:

- 建渠道 → 填 `base_url` → 编模型 → 授权 → **保存** → 回头进编辑 → 导入账号
- 其中 `base_url` 对 OAuth 账号并不重要, 却卡在最前面

改进: 渠道表单里把 `base_url` 标为"OAuth 账号可留空", 并在导入成功后
自动把该账号的平台建议填进渠道配置(仅当为空时)。

## 5. 流程三: 上架

现状路径: `Share` 页 → 渠道卡片 → 改价工作台 → 勾选 `listed` + 填供货价。

这条路径本身合理(上架 = 定价, 定价要在工作台里做)。问题在两处衔接:

1. **上架闸门只看审核, 不看账号是否可用**。一个渠道的全部账号都失效了, 它仍然可以上架,
   卖出去之后用户拿到 401。建议在 `ShareCard` 上加一个账号健康度提示:
   "该渠道 3 个账号, 1 个已失效" —— 不阻断上架(那是运营判断), 但必须可见。
2. **`Share` 页的渠道卡片与渠道管理页是两套视图**, 用户要在两处之间跳。
   建议在渠道卡片上直接给"管理此渠道的账号"入口。

## 6. 流程四: 运营(当前完全缺失)

这是最大缺口。账号接入之后的生命周期没有任何界面:

| 事件 | 现在的表现 | 应该有 |
|---|---|---|
| 令牌快到期 | 无感知 | 列表标"将到期", 可提前手动刷新 |
| 刷新成功 | 无感知 | `token_refresh_at` 更新, 详情可见 |
| 刷新失败(可重试) | 后台日志 | 列表标"刷新失败", 支持手动重试 |
| 账号失效(`invalid_grant`) | 后台告警, 凭据被熔断 | 列表标"已失效", 一键重导 |
| cookie 账号过期 | 无感知(本就不自动续期) | 明确标"需人工重导", 不等同于"正常" |

### 6.1 账号状态的四态模型

```
● 正常      到期时间在未来, 最近一次刷新成功
▲ 将到期    剩余有效期 < 阈值(比如 24 小时)
◐ 需人工     cookie 类, 或刷新连续失败但尚未判定失效
■ 已失效     刷新返回 invalid_grant 等终结性错误
```

这四态**全部可以由现有数据推出来**, 不需要新表: `AccountKind` + `TokenExpiresAt` +
`TokenRefreshAt` + 是否有 `DisabledUntil`(熔断标记)。

也就是说账号管理页**只缺一个列表接口和一个页面**, 数据层已经齐了。

### 6.2 需要的接口

| 接口 | 用途 | 现状 |
|---|---|---|
| `GET /api/v1/channel/account/list` | 跨渠道列出全部账号及其状态 | **缺** |
| `POST /api/v1/channel/account/import` | 导入 | 已有 |
| `POST /api/v1/channel/account/:id/refresh` | 手动刷新 | 已有 |
| `POST /api/v1/channel/account/:id/remove` | 删除账号凭据 | **缺**(可复用凭据删除) |

`list` 的实现很薄: 遍历 `channelKeyCache`, 过滤 `AccountKind != ""`, 按 scope 校验渠道归属,
拼上状态推导。**不需要查库** —— 这些数据本来就在缓存里。

## 7. 落点清单

按"先补缺口、再改入口"排序, 每项都独立可用:

| # | 改动 | 类型 | 依赖 |
|---|---|---|---|
| 1 | 凭据列表区分账号与静态凭据, 显示平台/到期 | 前端 | 无(数据已在 `ChannelKeyConfig`) |
| 2 | 渠道列表页加"导入账号"按钮 | 前端 | 无 |
| 3 | 导入对话框加目标渠道下拉 | 前端 | 无 |
| 4 | `GET /account/list` + 独立"账号"页 | 前后端 | 无(数据在缓存) |
| 5 | `ShareCard` 显示账号健康度 | 前后端(或前端聚合) | 需 4 的接口 |
| 6 | 导入时本地预检字段 | 前端 | 无 |
| 7 | 批量导入 | 前后端 | 无 |

第 1-3 项**纯前端**, 半天量级, 能立刻消除"找不到入口"和"看不见状态"两个最痛的问题。
第 4 项需要一个新接口 + 一个新页面, 但数据层复用现有缓存, 后端很薄。

## 8. 不建议现在做的

- **账号与渠道解耦(B 方案)**: 要新表 + 迁移, 而当前的痛点是入口和可见性, 不是模型不够抽象。
- **多 IP/并发调度**: 上游限流阈值没有公开数据, 只能等生产量起来再测。
- **cookie 账号的自动验活**: 需要"带 Cookie 打一个轻请求", 而轻请求的选择(哪个端点、
  算不算正常流量)对每个平台都不同, 且可能触发风控。这件事的风险大于收益, 建议保留人工。

## 9. 一个必须说清的前提

这套流程服务于"用自己的订阅账号接入"。若账号是买来的、或要转卖给他人,
则与上游 ToS 冲突(尤其是 OpenAI/Anthropic 的商用条款), 风险是大规模封号。
技术流程不改变这个前提 —— 设计上能做的是让"失效"尽早可见, 而不是规避条款。
