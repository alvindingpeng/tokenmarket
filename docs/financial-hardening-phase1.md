# 第一阶段：资金正确性加固

## 范围

本轮只加固已有资金流程，不部署、不自动修正历史余额、不自动重算已审核结算单。

- 预扣终态使用数据库条件迁移，结算与释放竞争时只能有一方更改冻结额；失败事务须连同状态和流水回滚。
- 管理员设置余额仍表示“设置目标总余额”，不是充值；差额必须以数据库当前值计算，冲突时拒绝或重试，不以缓存作为账本。
- 日配额检查和展示共用真实小时用量表与 time.Time 边界，使用本地自然日重置；这是已落库用量检查，尚不是在途请求原子日预算。
- 冷却期成熟收益排除已退款账单；提现不能因为退款仍被统计而提前释放未成熟收入。

## 日结退款口径

采用交易事件口径：原调用的供应商应收计入调用发生日；退款按批准日冲回原账单的供应商应收份额，而不是买家支付金额。退款日没有新收入的供应商也必须有调整单。净额允许为负，不能截断为零丢失债务；负额是财务调整，不代表系统会自动追偿或打款。

所有日期使用与现有对账一致的服务进程本地时区；一天按日历加一天计算，避免夏令时下固定 24 小时产生错位。部署时应显式固定业务时区。

重新生成只适用于未审核单据；已审核单据不能被静默覆盖。生成过程需要原子提交，查询或写入失败必须向调用者返回错误。

## 验证入口

`internal/op` 新增资金回归覆盖终态竞争、流水回滚、退款份额、跨期退款、仅退款账期、冷却期退款、缓存过期调账、配额表映射及夏令时边界。标准交付脚本 `scripts/check.sh` 增加 `go test -race -count=1 ./internal/op`，保证后续交付持续运行资金核心竞态检查。

## 上线前历史数据核查

1. 先做完整数据库备份。
2. 检查负冻结额、重复终态流水、重复请求关联以及余额人工调账差异；确认后以留痕调整修复，不能直接批量归零。
3. 比对退款原账单的 owner_revenue 与结算单退款扣减；本轮修复不会自动追溯更正旧单据。
4. 审核已打款和已审核单据，只对未审核账期人工确认后重新生成；跨期差异必须留调整凭证。
5. 验证启用日配额的 Key 能正常调用，并在达到阈值后拒绝。

## 历史只读核查 SQL（先在备份副本运行）

以下只定位疑点，不得将结果直接转换成批量调账；同一请求重复预扣等情况需结合请求日志判断。

```sql
-- 冻结额负数：可能存在历史重复解冻
SELECT id, balance, frozen FROM users WHERE frozen < 0;

-- 一个请求多条计费明细：结合 request ID 历史碰撞风险核查
SELECT request_id, COUNT(*) AS records
FROM billing_records GROUP BY request_id HAVING COUNT(*) > 1;

-- 同一请求多个预扣终态流水：核对是否重复操作或历史请求 ID 碰撞
SELECT request_id, COUNT(*) AS terminal_entries
FROM balance_ledgers WHERE kind IN ('settle', 'release')
GROUP BY request_id HAVING COUNT(*) > 1;
```

## 不包含

持久化失败结算重试、长请求预扣期限、实际 Token 预算预留、分布式请求 ID、全账本多余额快照、金额定点化属于后续工作。本轮也不宣称消除了退款发生在已打款之后的追偿风险，或完成 MySQL/Postgres 的并发实库验证。
