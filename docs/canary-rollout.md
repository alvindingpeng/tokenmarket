# 分组灰度分流（金丝雀）

## 为什么需要

新渠道/新模型接入后，管理员只有两种选择：整组切过去，或完全不切。整组切换一旦新渠道质量差，
所有流量一起受损；不切则新渠道永远拿不到真实流量，观测期与信任等级也就永远攒不出数据。
灰度分流解决的正是这件事：把一小部分流量定向放到新成员上，样本够了再决定是否全面切换。

## 与选择模式的关系

灰度是叠在现有选择模式之上的正交能力，**不是一种新的 mode**：

- 未命中灰度的流量完全按分组原本的模式选路，行为与不开灰度时一致；
- 命中灰度的请求只走配置的灰度成员，不参与价格/评分等策略比较 —— 否则便宜的老成员会把样本全部吃掉；
- 灰度成员当前不可用（渠道停用、凭据缺失、额度熔断、处于冷却或正被恢复探测）时，该轮直接回落原本策略，
  不会因为新渠道没就绪而卡住请求；
- 手动模式（manual）是人工硬约束，不参与灰度。

## 配置字段（relay_config）

| 字段 | 含义 |
| --- | --- |
| `canary_item_id` | 灰度成员的分组成员 ID（GroupItem.id）；0 表示关闭灰度 |
| `canary_percent` | 命中灰度的流量百分比，0-100 |
| `canary_user_ids` | 显式灰度用户 ID 列表；非空时这些用户恒定走灰度，优先于比例 |
| `canary_per_request` | 假（默认）按 API Key 粘性分桶，真则每请求重新抽样 |

## 命中判定

1. 未指定灰度成员或比例为 0：永不命中。
2. `canary_user_ids` 非空：只按用户判定 —— 列表内恒走灰度，列表外不走灰度。
   指定用户是"让这个人先用起来"的确定性安排，被比例稀释成概率就失去意义。
3. 比例为 100：全部命中。
4. `canary_per_request` 为真：按每请求随机种子抽样，用于只想要一点样本的场景。
5. 其余情况：以 API Key 主键（无 Key 时退化到用户 ID）做乘法散列，落进 100 个固定桶，
   桶号小于比例即命中。同一把 Key 的流量因此要么整体走灰度、要么整体不走。

粘性是刻意的：同一客户端若在两条路径间来回抖动，长对话会被拆到两个上游，上下文缓存全部丢失，
灰度样本也不再代表"某个用户在用新渠道"。

## 失败与回落

- 灰度成员失败一次后，本请求内不再走灰度，后续轮次完全回落到原本的选择策略；
- 灰度成员的失败照常计入渠道/模型统计并触发既有冷却与熔断，与普通成员无异；
- 命中但成员不可用的轮次在请求日志里留一条 `canary_unavailable` 事件，
  与"没抽中"区分开，便于判断灰度是不是真的在产流量；
- 路由解释中，灰度选中的轮次记为 `canary_rollout`，不会被误读成"评分恰好选了它"。

## 观测与推进节奏

建议的推进方式：先 `canary_percent` 5-10 观测一天，看成功率和首响应耗时是否与主渠道可比；
再抬到 30-50 观测，最后切到 100 或直接改成常规成员。灰度期间路由状态（冷却、亲和、探测）
对灰度成员照常生效，因此不需要另设一套开关。
