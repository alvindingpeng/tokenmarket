# 生视频支持(P2)

## 范围

为 OpenAI Videos 协议提供完整的转发与按次计费:

- 协议位 `ProtocolOpenAIVideo = 1<<5`, 路由, 授权矩阵, 出站转换全部接入。
- `POST /v1/videos`: 创建任务, 同步返回任务对象(状态通常为 `queued`)。
- `GET /v1/videos/{id}`: 查询任务, 客户端据此轮询取回视频地址。
- `DELETE /v1/videos/{id}`: 取消任务。
- 计费: 按条固定价 + 按时长计费, 分辨率分档可选。
- 预扣: 按请求声明的 `seconds` 冻结「每条用户价 + 时长 × 每秒用户价」。

## 定价机制

媒体模型不走 token 计价, 三个维度各自独立, 按形态取用:

| 字段 | 含义 | 适用形态 |
|---|---|---|
| `per_image` | 每张单价 | 生图 |
| `per_video` | 每条固定起步价, 与时长无关 | 生视频 |
| `per_second` | 每秒时长单价 | 生视频 |
| `resolution` | 分辨率分档价, 命中时覆盖 `per_image` / `per_second` 的单价 | 生图与生视频 |

结算公式:

- 生图: `张数 × (分档价 或 per_image)`
- 生视频: `条数 × per_video + 秒数 × (分档价 或 per_second)`

`resolution` 是与时长无关的起步价之外的加成, 因此**不参与分档** —— 分档描述的是「这一档每秒/每张多少钱」,
把它套到起步价上会让同一档位的含义变得含糊。

分档键由 `resolution` 字段显式给出, 缺失时由 `size` 的短边推出(`1280x720` 与 `720x1280` 都归到 `720p`),
使横屏与竖屏落到同一个价位。两者都缺时按不分档的单价计费。

## 关键设计

### 形态跟着协议位走

渠道模型的媒体形态(`ChannelModel.Kind`)由授权协议位推导:

- 任一 `(模型 × 凭据)` 授权带生视频位 ⇒ 该模型 `kind=video`, 优先于生图位与能力登记 —— 这是管理员的直接授权意图。
- 生图位 ⇒ `kind=image`; 能力登记里只输出视频的模型即使没勾任何媒体位也落 `kind=video`。
- 媒体位全部撤销 ⇒ 回退文本。保存渠道时在 `syncChannelModelKinds` 统一重算。

### 出站地址是基路径而不是完整路径

出站转换器对视频固定拼接 `{BaseURL}/videos`(创建)与 `{BaseURL}/videos/{id}`(查询/删除), **不接受完整路径**,
因此渠道配置里是 `openai_video_base_path`(默认 `/v1`)而不是像其他协议那样的完整路径字段。
归一化时去掉结尾斜杠, 避免拼出双斜杠; 只填 `/` 表示视频直接挂在域名根下。

### 异步任务需要归属追踪

这是生视频与生图最根本的差别: 生图一次请求就拿到图片, 而生视频的查询请求(`/v1/videos/{id}`)**不带模型名**,
无法像创建那样按模型名解析分组与成员。

因此创建成功时把归属落库到 `video_jobs`(`job_id` / `user_id` / `group_id` / `channel_grant_id` / `channel_key_id` / `model_name`),
查询与取消时按任务 ID 取回, 直接定位创建它的那个渠道授权与**创建时实际使用的凭据**。
凭据会轮换(换绑授权、停用旧凭据、按策略挑选), 只记授权会在轮换后用「当前凭据」查不回任务,
因此凭据以 ID 一并落库(不落明文), 查询侧优先按它还原同一把凭据; 老记录(`channel_key_id` 为 0)回落授权绑定的凭据。
任务 ID 只对创建它的那家上游有效,
所以定位失败时回 503 而不是退到别的成员 —— 换渠道查必然查不到, 只会把「查无此任务」伪装成上游的答复。

任务不属于当前 API Key 归属者时与任务不存在返回同一个 404, 否则任务 ID 会变成探测他人任务的工具。
归属记录保留 24 小时后由定时任务清理, 与上游任务自身的过期时间同量级。

### 计费时点: 创建时结算

生视频的费用在**创建任务时**按上游回显的时长结算, 而不是等任务完成。这是刻意的权衡:

- 上游在创建时就已接受任务并开始消耗算力, 网关此刻已经产生成本;
- 若改成完成时结算, 客户端只要不轮询就永远不会结算, 会产生永远不入账的用量;
- 结算用量优先取响应回显的 `seconds`(实际产出时长可能与请求不同), 未回显才回落到请求声明的值。

代价是任务后续生成失败时费用已经产生。要消除它需要跟踪每一次轮询并在失败时冲正,
那会让计费依赖客户端是否回来查询 —— 对账口径反而更不可靠。

查询与取消**不计费**: 轮询是客户端取回结果的必要动作, 按次收费等于让用户为等待付费。

### 转发

- 生视频请求的正文改写: 与其他 JSON 协议一致, 用 `sjson` 改 `model` 字段为上游模型名。
- 生视频不走跨协议回退: 客户端发起的生视频请求只能由带生视频位的授权承接,
  回退到 chat/response/anthropic 只会把视频请求转成聊天请求打向错误端点。
- 不支持流式: 生视频的「异步」体现在任务对象上, 由客户端轮询取回, 不是流式响应, 带 `stream` 的请求直接拒绝。
- 限流估算: 与生图一致按 `(1,1)` token 预留, RPM 与并发才是真正的约束。

### 计费落库

- 预扣(`reserveBalance`): 分组内 video 成员的 `每条用户价 + 时长 × 每秒用户价`,
  时长取请求声明的 `seconds`, 未声明时按保守默认值 `defaultVideoReserveSeconds`(10 秒)冻结。
- 时长的有限上界: 解析、预扣、结算只接受 `(0, maxVideoSeconds]`(4 小时)内的秒数, NaN / Inf / 越界值一律不当作时长,
  任何路径都不进金额计算; 合法时长原样计费, 不做截断 —— 计费时长必须与转发给上游的时长一致。
  声明了非法 `seconds` 的请求由 `POST /v1/videos` 路由上的时长闸门(`VideoCreateDurationGuard`, 挂在转发之前)以 400 拒绝 ——
  既不冻结余额也不发往上游, 而不是按别的时长计费再转发原值; 压缩正文按同一套解码解开后校验, 不能绕过闸门。
- 结算(`settleBillingLocked`): `user_cost = token费用 + 每条用户价 × 条数 + 每秒用户价 × 秒数`;
  `owner_revenue` 同口径按供货价; `price_source = channel_model_media`。
- `BillingRecord.MediaUnits` 记 `{videos, seconds, resolution}`, token 四列保持 0。
- 统计: 媒体费用折入输出侧桶, 图表口径不变。

## 管理后台

- 渠道配置: `openai_video_base_path`(默认 `/v1`)。
- 改价工作台: 生视频模型显示「每条价」与「每秒价」两个输入, 右侧同时给出两个用户价。
- 上架校验: 生视频模型 `per_video` 与 `per_second` 全 0 且无分档价时, 上架被拒绝(与生图同一收入口径)。
- 统一倍率一键改价**不覆盖媒体模型**: 官方价格表是 token 口径, 用 token 价覆盖媒体价会把收入口径改错,
  改价预览里以 `media_model` 原因跳过。
