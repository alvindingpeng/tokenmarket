# 审核指纹补入供给字段 —— 迁移 46 的语义与能力上限

> 范围: 渠道准入审核(P1)的指纹口径修正。本文记录两件事: 为什么 `openai_video_base_path` 与
> `sub_platform` 必须进指纹, 以及**已经过审的存量渠道怎么处理**——迁移 46 以迁移当日的现状为新基线。
> 前置文档: [design-channel-review-observation-quality.md](design-channel-review-observation-quality.md)(审核与观察期整体设计)。
> 本文只覆盖指纹口径与基线迁移这一段, 不改动审核状态机、观察期与门禁的任何语义。

## 1. 漏了什么, 以及漏掉的后果

指纹的作用是"审核看到的那份供给面, 之后有没有被改过"。它只对「会改变供给行为」的字段取值:
`dialect` + `base_url` + 协议路径 + 模型清单。修正前有五条 OpenAI 路径与一条 Anthropic 路径,
**但少了两项会直接改变供给的东西**:

| 字段 | 它决定什么 | 漏进指纹的后果 |
| --- | --- | --- |
| `openai_video_base_path` | 视频请求落在哪个基路径(转发在其后拼 `/videos`、`/videos/{id}`) | 已过审渠道改掉它 = 视频这一路换上游, 但仍以 `approved` 对外暴露, **零复审直接生效** |
| `sub_platform` | 订阅渠道的平台标识: 账号平台、凭据种类、上游地址装配全由平台描述给出 | 换平台等于整条供给链换供应商, 却与"改了个标识"同等对待, 指纹比对看不见 |

两者的共同点不是"它们是配置项", 而是**改了之后用户拿到的商品就不是同一件了**。判据应当写成
"这一项改了, 东西还是不是原来那个东西", 而不是"这一项是不是一个字段" —— 后者会把
价格与代理也拉进来, 于是渠道商每次调价都要复审(见第 4 节的反向约束)。

## 2. 迁移 46 的语义: 认现状为基线

补进两个字段之后,**运行期算出来的指纹与库里存的旧基线必然不等**。旧基线是按旧口径算的,
新口径多了两行哈希输入。于是产生了这次选择:

- 方案 A(不改): 全部已过审渠道会在**下一次人工保存**时被比对判成失配, 集体转 `stale`。
  这些渠道一个字都没改, 却要人工重新走一遍复审 —— 公开面几乎全停摆, 复审队列被淹掉。
- 方案 B(**本次采用**): 迁移 46 跑一次, 用**迁移当日的库内真实配置**重算出新口径指纹,
  覆盖 `config_fingerprint`。此后运行期算出的值与之相等, 不会误报。

也就是说: 迁移 46 的语义是"**把此刻的库里状态当作审核看到的样子**", 做一次性的基线推进。
这也是它为什么必须由迁移来做 —— 它不是业务动作, 是口径变更后的数据对齐, 且只该发生一次。

### 2.1 处理范围与"不做什么"

只处理 `review_status=approved AND shared=1`(已过审且已发布)的渠道: 只有它们的基线代表
"审核看到的样子"。其余一律不动, 理由逐条:

| 状态 | 为什么不重算 |
| --- | --- |
| `draft` / `pending` / `rejected` | 没有基线语义 —— 还没被审过, 谈不上"审核看到的那份" |
| `stale` | **有待复审的失配态**。重算会把"待复审"抹成"已审", 等于替管理员批准了一条他没看过的配置 |
| `approved` 但 `shared=0` | 不在公开面, 不存在"漏审即新暴露"的问题; 保持不动, 让它下次保存时自行对齐 |

迁移只写 `config_fingerprint` **一列**: 不改 `review_status`, 不把任何渠道置 `stale`, 不碰配置列,
不动 `shared`。它是"对齐基线", 不是"复审"。

### 2.2 幂等与安全跳过

两条要求都来自生产事实: 迁移失败后服务会重启, 同一个 `Up` 会被再跑一遍; 而库可能是
只跑到一半的形态。

- **幂等**: 逐条比对, 与库里已存值相同的行不写库; 一条都没写就不写审计。重跑零副作用。
- **表/列缺失即跳过**: `HasTable("channels")` 与 `HasColumn(...)` 双重判定(表、`config_fingerprint`、
  `review_status`、`shared`、`dialect`、`base_url`、`openai_video_base_path`、`sub_platform`)。
  缺列时**整条跳过**, 不拿空串凑一个"看起来对"的指纹 —— 那种值必然与运行期算出的不等,
  等于制造一次全部渠道转 `stale`, 而原因藏在迁移里, 现场查不出来。
- **SQL 方言中立**: 只有 GORM 的读写与 `UPDATE channels SET config_fingerprint = ? WHERE id = ?`,
  不依赖 SQLite/MySQL/PostgreSQL 任何一家的专有语法。

### 2.3 口径只有一份实现

指纹算法沉到 `internal/model`: `model.ChannelConfigFingerprint(config, modelNames)`。
op 层保留 `channelConfigFingerprint` 作为一层转调(op 内十余处调用点都以它为准), 迁移直接调 model 那一份。

这不是风格问题: `internal/db/migrate` **不能** import `internal/op`(`op -> db -> migrate -> op` 成环)。
若两处各写一份实现, 它们必然漂移, 而漂移的表现正是"迁移算出的基线与运行期算出的指纹不等",
也就是本迁移想要消除的那个故障。

新实现相对旧实现**只是多了两行哈希输入**(`videobase=` / `subplatform=` 插在协议路径之后、
模型清单之前), 行序、排序去重与路径归一口径一字未动。这一点由单元测试钉死: 固定夹具的
"旧前像"哈希必须仍等于加字段之前线上真实的基线值, 新实现的哈希必须等于另一个固定常量。

## 3. 能力上限: 迁移之前的静默改动无法追溯

这是本方案必须承认的代价, 写在最前面而不是藏在脚注里。

**事实**: 在迁移 46 跑之前, 若有人已经静默改过某条已审公开渠道的 `openai_video_base_path` 或
`sub_platform`, 我们**查不出来**。理由是系统里不存在能回答这件事的数据:

| 缺什么 | 为什么补不出来 |
| --- | --- |
| 历史配置快照 | 渠道表只有当前值, 没有版本表, 也没有逐字段的历史 |
| 那两个字段的改动审计 | 当时的 `ChannelUpdate` 只记动作与目标, 不记"哪一列从什么改成了什么" |
| 变更时间点 | 迁移能读到的是迁移时刻的值, 与改动发生在什么时候无关 |

因此迁移 46 后的基线里,**这两个字段的历史状态是"未知"而不是"已确认与审核时一致"**。
在迁移当日之前, 这两个字段的审核覆盖强度等于零 —— 这是本次修正之前就存在的缺口, 不是修正引入的。

**为什么仍然选"认现状"而不是"全部置 stale"**: 把全部已审公开渠道一次性打成 `stale` 会让公开面
几乎全部需要人工复审, 而没有任何证据说它们真被改过 —— 那是用一个确定的大面积停摆, 去换一个
概率未知的漏审。两害相权, 认现状并把"此后任何改动都会触发复审"做实, 是更可解释的一边。
这个取舍的边界很清楚: **从现在起可追溯, 在此以前不可追溯**。

## 4. 反向约束: 口径不许放大

把整个配置结构体哈希一遍能让"补上两个字段"这件事看起来解决得很彻底, 代价是渠道商每次
调价、换代理、加 Header、改参数覆盖都会触发复审。因此指纹**刻意不含**下列字段, 且这一点
同样由测试钉住(改这些字段后指纹必须一字不变):

| 字段 | 不入指纹的理由 |
| --- | --- |
| `markup_ratio` / 供货价 | 改价已有 `models/reprice` 审计链路; 价格高频调整, 卡审核等于让复审队列停摆 |
| `channel_proxy` / `proxy` / 出口池 | 变的是"怎么把请求发出去", 不是"卖给用户的是什么"; 运维天天在调 |
| `custom_header` / `param_override` | 同上 —— 出站形态属运维配置 |
| `gemini_project` | 由探测自动回填的运维字段, 人工也可能改; 它不改变上游供给面 |
| `enabled` / `model_auto_add` | 启停与自动发现是运营动作, 不产生新的对外供给(自动发现只增不删、默认不上架) |

判据一句话: 改完之后"同一个模型名在用户侧是不是还代表同一件商品"。是, 就不进指纹。

## 5. 此后会发生什么(新行为)

迁移 46 之后, 已过审公开渠道的这两项进入可追溯状态:

- 任何对 `openai_video_base_path` 的改动, 在下一次 `ChannelUpdate` 保存时即被指纹比对发现:
  渠道商渠道转 `stale`(复审前不新增暴露, 存量分组成员流量不中断); 管理员免审渠道直接换基线。
- 任何对 `sub_platform` 的改动同理。
- 两条路径都会写 `channel.review_stale` 审计(动作固定, detail 为 `config fingerprint mismatch`),
  与既有的 `channel.review_submit` / `_approve` / `_reject` 同一条链路。

## 6. 留痕: 基线是被推进过的

迁移 46 在审计表写一条记录, 动作 `channel.review_fingerprint_baseline`(`user_id=0`, 系统动作),
`target=channels`, detail 里带**重算条数**、**examined** 与**原因**, 形如:

```text
recomputed=<N> examined=<M> reason=审核口径指纹纳入 openai_video_base_path 与 sub_platform, 迁移 46 以迁移当日现状为新基线; 之前的静默改动无法追溯
```

为什么需要它: 基线被整体推进这件事本身必须留在数据里, 否则半年后无法回答"这个渠道的基线为什么
与当初审批时的那份不同"。重算 0 条时不写这条记录(重跑不该在审计表里堆空行)。
审计写失败只记日志、不回滚指纹: 基线已经推进且是对的, 少一条记录不该让启动失败。

## 7. 落地清单

| 位置 | 改动 |
| --- | --- |
| `internal/model/channel_fingerprint.go` | 指纹的**唯一**实现 `ChannelConfigFingerprint`, 补两行哈希输入, 函数头写清判据 |
| `internal/op/channel_review.go` | `channelConfigFingerprint` 降为转调, 语义留在 op 层 |
| `internal/db/migrate/046_channel_fingerprint_supply_fields.go` | `Version 46` 基线重算: 只改一列, 幂等, 缺表缺列跳过, 写审计 |
| `internal/op/channel_review_test.go` | 两条 stale 正例(视频基路径 / 平台标识), 一条非供给字段反例, 一条算法等价性夹具 |
| `internal/db/migrate/046_*_test.go` | 重算正确性 / 幂等重跑 / 缺表跳过 / 缺列跳过 |

## 8. 已知边界

- 迁移只覆盖迁移**当日已过审且已发布**的渠道。此后才过审的渠道由审批流程写基线, 口径已新, 无需迁移。
- `approved` 但未发布(`shared=0`)的渠道保持旧基线: 它下次保存时会被比对发现失配并转 `stale`,
  但那条渠道本就不在公开面, 不存在漏审即新暴露; 若它随后被发布, 发布前必须已过审, 闸口不会放行旧的。
- 迁移不改变"指纹只用于已过审渠道"这一前提: `draft`/`pending`/`rejected` 无基线语义。
