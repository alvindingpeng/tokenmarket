# 渠道模型改价工作台

入口: 管理后台 > 发布管理(`/share`) > 选中渠道 > 模型上架与定价。改价直接决定渠道商供货价, 而用户价 = 供货价 × (1 + 全局上浮比例), 因此这一处既是收入口径也是计费依据。

## 一、界面能力

| 能力 | 说明 |
|---|---|
| 用户价实时预览 | 每行除四类供货价外, 显示**用户实际支付单价**(输入/输出), 由 `markup_ratio` 当场换算, 不必心算或切页 |
| 搜索 | 按模型名过滤; 上百个模型不再靠滚动 |
| 筛选 | 全部 / 仅已上架 / 仅未上架 / 仅未定价 —— 未定价是最需要盯的一类 |
| 改动计数 | 相对服务端数据的真实改动数, 无改动时保存按钮不可用, 避免无谓写库与无谓审计 |
| 零价上架拦截 | 已上架但四价全 0 的行标红, 并**禁用保存**; 后端同样拒绝, 前端先行提示 |

关键实现细节: 视图是筛选后的子集, 而草稿是完整清单 —— 行按**名称**回查真实下标, 避免筛选状态下改错行; 保存始终提交全量清单, 筛选绝不能成为漏改价格的原因。

## 二、后端校验

`ChannelModelListingUpdate` 对每个被提交的模型校验:

1. **价格非负** —— 负数会让用户反向获利;
2. **价格有上限** —— 单类每百万 token 上限 `1_000_000`, 越界基本是少打小数点;
3. **已上架必须有价** —— 上架即对用户可见, 而四价全 0 就是按 0 计费, 属于实打实的收入泄漏, 直接拒绝。

错误以 400 返回并指明字段, 例如 `input supply price cannot be negative` / `channel model m-up is listed but has no supply price`。

## 三、改价可追溯

`POST /api/v1/channel/models/update` 的响应新增 `changed` 数组, 只回报**真正变化**的行与字段:

```json
{ "code": 200, "data": { "changed": [ { "name": "m-up", "detail": "input: 1 -> 3.5" } ] } }
```

同一份差异同时写入审计(`action=channel.model-price`, `target=channel#<id>`, detail 为 `模型 字段: 旧 -> 新`), 可在审计页按动作筛选查看。要点:

- **只记变化行** —— 整体提交的语义是"这份清单生效", 但审计要回答的是"谁把哪个模型的价格从多少改成了多少"; 逐字段比对后未变动的行不进审计, 否则每次保存都会写几十条噪声。
- **无改动不写审计** —— `changed` 为空时不产生审计记录, 重复保存同一份清单不留痕。
- 历史账单不受后续改价影响: `billing_records` 存的是结算当时的 `supply_price` / `user_price` / `markup_ratio` 快照。

## 四、验证

`octopus-e2e-billing.py` 106/106, 本项新增 12 条: 负数/超上限/已上架未定价三种非法提交均 400; 真实改价返回 200 且回执只含目标模型; 回执带 `旧 -> 新`; 重复保存同一价格回执为空; 审计写入且 detail 含差值; 价格复原成功。
