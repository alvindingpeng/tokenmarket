# 日结锁冲突与近七天补偿（v1.4.2；事务形状更新于 v1.10.16）

## 原因与修复

日结的形状决定了它撞上哪种锁错误。**v1.10.16 之前**：一个事务里先按日聚合账单、再写结算单。
SQLite WAL 下其他写者提交会使旧读快照无法升级为写事务，`busy_timeout` 不覆盖这条路径
（`SQLITE_BUSY_SNAPSHOT`，517），只能整事务回滚重来；而窗口宽度等于整表聚合耗时，并发下几乎必然失败。

**现在的形状（v1.10.16 起）**：
1. 聚合读（当日毛额 + 当日批准退款 + 退款原账单）放在**一个只读事务**里 —— 只为拿到同一快照，
   在 WAL 下只持读快照、永不升级、不挡任何写入者；
2. 写事务只做"读几行已有单据 + 写几行结算单"，**第一条语句就取写锁**（`db.AcquireWriteLock`），
   让并发的日结/审核在锁上排队，而不是让自己的读-写升级去撞 517。

语义上因此多了一个**明确的时间窗**：聚合读发生在取锁之前，期间新落库的明细属于下一次重算
（幂等 upsert 会补齐）。这是有意的取舍 —— 用"晚一轮看到最后几条"换"不再失败"。

原子性没有损失：结算单不可变由 `settlementWriteRow` 的状态守卫（条件更新）保证，
已审核单的差异校验也在持锁的写事务里重新读当前行。

仅 SQLite BUSY/LOCKED 允许最多**八次**完整事务尝试（退避 10ms 起指数增长、截顶 500ms，
叠加 `[0, 上界/2)` 的正向抖动，可被 context 取消）。八次只是**兜底**：单靠拉长窗口
实测仍会失败（8 次里失败 6 次），真正起作用的是上面的锁获取顺序。
已审核差异、源数据损坏、其他数据库错误不作为瞬时锁重试。金额与退款归属沿用原口径，
已审核单不覆盖，生成不触发付款。

## 补漏边界

- 启动及每小时检查服务本地自然日的昨天至前七天，从最旧账期开始。
- 成功后写入持久账期检查点；失败不标记成功，下轮仍会尝试。一个账期失败不阻塞其他账期。
- 生成成功但检查点写入失败会安全重跑，依靠原结算单唯一键与审核保护保证幂等。
- 首次部署会检查近七天尚无检查点的账期；不会自动重算七天以外的历史账。
- 成功检查点不是账本封账或付款凭证。标记成功后又到达的历史数据、迟到退款修订和七天以前的漏单，仍需管理员按原有审计流程核对。
- 同进程补偿串行执行；不宣称支持多实例强单飞。跨实例依赖原事务/唯一约束及审核保护。

## 生产核验

只读脚本检查健康状态、近七天源账单及结算单数量与金额摘要，不调用生成接口、不修改资金。发布后可设置 `REQUIRE_CHECKPOINTS=1`，缺任一账期成功检查点即以非零退出。不能仅凭健康为 ok 或账单数量相同宣称财务对账完成。

部署前（2026-11-01）只读检查发现 20261025 有 26 条账单、无结算单；20261031 的结算请求数为 525，与该日源账单数量一致。该结果不包含金额及退款全量对账。

部署后（v1.4.2 / 770ab7e）严格检查通过：20261025—20261031 七个账期均有一个成功检查点；20261025 自动补出一张单，26 个请求，毛额/净额 0.03524373719999999，退款 0。其他六天的请求数、毛额、退款及净额与部署前逐项相同。生产已审核单数量为 0，部署前后全字段摘要相同；已审核保护以真实并发回归测试补充验证。未手动调用生成或付款接口。服务健康 v1.4.2 / db=ok，公网匿名页面浏览器冒烟通过。
